# Guardrails

- Verify with the dev server and quick checks. Don't build verification scripts or take screenshots for cosmetic changes unless asked. If a check fails twice, stop and report it instead of continuing to investigate.
- No headless-browser screenshots for visual checks (spacing, line wraps, layout) unless explicitly asked, and even then keep it to one or two shots, not an iterative loop. Reason from the CSS instead, or just make the change and let the user look at it.
- Don't spawn subagents for verification or exploration.
- The user can see and click the running app themselves. Don't re-fetch pages or parse rendered HTML to confirm what they can eyeball in five seconds. Only chase things that could be silently wrong without a visible symptom: type errors, data wiring, state logic.
- Don't add dependencies, component libraries, or anything beyond what SPEC.md lists unless asked.
- Work in small, reviewable chunks. Stop and summarize what changed after each one rather than running long unattended.
- Commit only when the user says so.
- Once a dev server is started for the user to test against, leave it running in the background. Don't kill it after your own verification checks — the user tests in the same running instance rather than starting their own.

## Project reference

- `SPEC.md` is the authoritative build spec: the original take-home brief (quoted verbatim at the top — never edit that section, even when it uses wording the app has since diverged from) plus every decision layered on top since. Check it before making UI/behavior calls; several sections already document explicit, deliberate departures from the original brief's own wording.
- `mock-data.json` at the repo root is a verbatim, untouched reference copy of the seed data as originally provided. The app doesn't import it — `src/data/mock-data.ts` is the typed module actually consumed by the code, kept in sync by hand.

## Conventions established so far

- **Terminology is "claimed", full stop.** This flip-flopped through "assigned" for a while (both in display copy and, briefly, in the `Allotment` field name itself) before landing back on `claimed` everywhere — the data field (`types/guest-tickets.ts`, `data/mock-data.ts`, the hook, component props) *and* every rendered string ("X of Y claimed", "All tickets claimed", the slot-group `aria-label`s, the disabled-button reason). There's no split anymore; SPEC.md's Data model section has the reasoning (matches both `mock-data.json`'s key and the brief's own "2 of 5 claimed" phrasing). "Reassign" is a separate word for a separate action and was never part of this — don't touch any instance of it when doing terminology sweeps.
- **No trailing periods on short UI copy** — headlines, status lines, button-adjacent text (e.g. "All 5 tickets have been claimed", "Not armed"). Full sentences in dialog body copy and error messages keep periods (e.g. "We couldn't save your guest." / "Please try again.").
- **Dialog error/description copy is passed in as props, not hardcoded.** `GuestFormDialog` takes `title`, `description`, `errorTitle`, `errorDescription` from its caller rather than deriving them internally from a mode switch, so Reassign (and any admin-side reuse) can supply its own wording without editing the shared component. Each action's error copy is intentionally distinct ("couldn't save" for Add/Reassign, "couldn't remove" for Remove) — don't consolidate to one shared string.
- **Dialog footer button order:** the primary action (Save/Reassign/Remove) comes before Cancel in JSX/DOM order. That makes Tab land on it right after the last field when it's enabled, and fall through to Cancel via native disabled-button skipping when it's not. Tailwind `order-1`/`order-2` classes restore the usual visual layout (Cancel first/left, primary action last/right) without touching tab order.
- **`AlertDialogAction`'s `className` prop only reaches the inner Radix element, not `Button`'s own class computation** (it renders `<Button variant size asChild><AlertDialogPrimitive.Action className={...} /></Button>` without forwarding `className` to `Button` itself). A plain color override on `AlertDialogAction` will silently lose the cascade to the default variant's classes — use Tailwind's `!` important suffix (e.g. `bg-destructive!`) to force it, as the Remove button does.
- **`AlertDialogHeader` centers its content by default below the `sm` breakpoint** (`place-items-center text-center`, only switching to left-aligned at `sm:` and up) — add `place-items-start text-left` explicitly if you need left alignment on mobile, as Remove's title does.
- **`Label` is a flex container with `gap-2` built in.** Don't add a literal space (or other manual spacing) between label text and adjacent inline content (badges, required-asterisks) — it stacks with the flex gap and doubles the visual space. Override `gap-0` on the specific `Label` and use an explicit margin on the child instead if the built-in gap is wrong for that instance.
- **Dialogs are capped at `max-h-[85dvh] overflow-y-auto`** from the start, not retrofitted — avoids the on-screen-keyboard-covers-Save problem SPEC.md's Accessibility section calls out.
- **Email validation** is pragmatic (`/^[^\s@]+@[^\s@]+\.[^\s@]+$/`), validates on blur/submit rather than every keystroke, and blank is always valid since email is optional.
- **Devtools is a floating icon + popover, not a panel.** `src/components/demo/demo-controls-panel.tsx` lives outside the product component tree on purpose — a small muted wrench icon fixed bottom-left (closed by default, never persisted across reloads), expanding into a popover with a "Simulate a save error" button. That button arms the *next* add/reassign/remove attempt (via `useGuestTickets`'s `armNextFailure`) to fail once, then auto-disarms. There's no automatic or random failure — this is the only way to reach the save-error state. Don't add animation to it and don't let it read as a product feature (no fill/shadow the real "Add guest" button doesn't also have).

## Visual design tokens (`src/index.css`)

Four custom tokens on top of the shadcn Nova theme, all added for Tassel brand fidelity — check the actual current hex values in `index.css` before reusing, the comments there explain the contrast reasoning:
- `--page-background`: warm cream page background, distinct from the white `--background`/`--card` used by chrome and cards.
- `--hairline`: the *decorative* border shared by cards and the header/footer — plain white-on-cream is only ~1.1:1 contrast (unreadable as an edge), so this is deliberately lighter than a strict 3:1 read, a legibility-over-invisibility tradeoff, not a compliance target.
- `--hairline-interactive`: a darker step of the same hue, used only by the open ticket-slot buttons. At the plain `--hairline` shade they read as disabled rather than tappable — interactive elements and decorative borders ended up needing different weights.
- `--brand`: the exact Tassel orange, scoped to exactly one place on purpose — the filled ticket slots. It does **not** appear on any button: white text on it fails WCAG AA at normal button-text sizes (~3.34:1 vs 4.5:1 required), so buttons stay on the existing dark-fill/white-text treatment rather than fighting that tradeoff. If you're tempted to add brand color to a new element, check contrast against its actual background first — don't assume the hex "just works" the way it does on Tassel's own marketing site, where text is often sized/weighted differently.

## Motion (added in a dedicated pass, small and purposeful)

- **`prefers-reduced-motion` is one global rule in `index.css`**, not per-element `motion-reduce:` variants — a top-level (outside `@layer`) media query forcing all `animation-duration`/`transition-duration` to ~0. Add new animations without worrying about individually tagging them; the global rule already covers it. A couple of explicit `motion-reduce:` variants exist anyway on the spots most likely to still show an artifact at near-zero duration (button press scale, guest-row collapse) — that's belt-and-suspenders, not required per-animation.
- **Live transitions are distinguished from initial mount/load via a `hasMountedRef`**, in both `TicketSlot` (checkmark scale-in) and `GuestListCard` (row add/remove). Guests already claimed/present on first load must never replay an animation meant to confirm a *live* action — that moment is already covered by the skeleton-to-content crossfade. If you add another animated state change, follow the same pattern rather than animating on every mount.
- **`TicketSlot`'s checkmark reveal is deliberately delayed (`REVEAL_DELAY_MS`)** past when the underlying data actually changes, because the action that fills a slot (Save) also closes its dialog, which plays its own close animation on top. Without the delay, the checkmark's animation plays out entirely hidden behind the closing dialog. If a similar "confirm after a dialog closes" animation gets added elsewhere, budget a similar delay rather than triggering immediately on data change.
- **Height can't be transitioned to/from `auto` in CSS directly.** Guest row add/remove uses the `grid-template-rows: 0fr` ↔ `1fr` technique (grid container + a child with `overflow-hidden`) rather than a JS-measured pixel height. Reuse this pattern for any future collapse/expand rather than reaching for a measurement-based approach or a library.
